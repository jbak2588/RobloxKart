# KDM Shared HUB Racing Park — 에셋 추출 및 구현 설계안

작성일: 2026-10-21 · 상태: **구현 전 검토용 제안서**

Repository: `jbak2588/RobloxKart`

Branch: `prototype/kart-physics`

검토 기준 HEAD: `17e916a370fd0bfaad19b7e09b594cb8f898ebd5`

이 문서는 무엇을 추출하고 어느 코드를 어떻게 바꿀지 설명한다. 문서 작성이
아래 기능 전체의 구현·정책·게시 승인을 의미하지 않는다. 이번 변경에는 에셋
추출물, 게임 코드, Studio 변경, Roblox Publish가 포함되지 않는다.

## 1. 만들려는 경험

HUB를 카트 선택 후 떠나는 대기실에서 **카트를 타고 머물 수 있는 레이싱 파크**로
발전시킨다. 기존 Lobby 건물이 중심이며, 그 주변으로 주행 코스가 연결된다.

사용자가 제공한 첫 번째 이미지는 외부 안내판·피트·조경·랜드마크가 결합된
공간 구성을, 두 번째 이미지는 Lobby를 끼고 반복 순환하는 코스 구성을 참고한다.
이미지의 도로 형태나 건축물을 그대로 복제하는 최종 도면으로 취급하지 않는다.

핵심 경험은 다음과 같다.

1. HUB에 도착하면 자신의 카트를 생성하고 쉽게 탑승할 수 있다.
2. 공식 RACE에 참가하지 않아도 Lobby 주변 코스를 계속 순환할 수 있다.
3. 같은 HUB 서버의 다른 플레이어가 실제로 달리는 모습을 볼 수 있다.
4. Lobby 밖에서 TRACK VOTE, LEADERBOARD, GARAGE와 RACE 진입 지점을 찾는다.
5. 공식 RACE에 참가하거나 자유 주행으로 돌아가는 짧은 반복 흐름을 유지한다.

HUB 자유 주행은 공식 RACE와 다르다. 순환 횟수가 늘어도 자동으로 공식 랩 기록이나
K$를 지급하지 않는다. 기존 승인된 시승 보상·자격 판정은 그대로 보존한다.

## 2. 이번 조사에서 확인한 사실과 미확정 사항

### 확인한 사실

- `C:/dev/rbxlx_data`에 아래 네 개의 `.rbxlx` 파일이 있다. XML을 읽기 전용으로
  분석했으며 원본 내 스크립트를 실행하지 않았다.
- 현재 공유 시승은 `LobbyTestDriveService`가 플레이어별 카트·입력·탑승·정리를
  관리한다. 빈 시작 슬롯을 찾고 카트 간 비충돌을 적용한다.
- `LobbyDriveGeometry`와 `LobbyFrontDriveZoneBuilder`는 현재 Lobby 주변의 평면
  영역과 도로·경계 형상을 만든다. 고저차가 있는 다층 주행 판정은 구현되어 있지 않다.
- 기존 시승 코드에서 전체 주행 시간을 제한하는 고정 타이머는 발견하지 않았다.
  다만 이탈·사망·상태 변경·경계 이탈 등 정상 종료/복구 조건은 존재한다.
- `HubUiController.onRaceNow()`는 `LobbyDriveActive` 또는 진입 대기 중이면
  실행을 거부한다. 주행 중 버튼을 추가하는 것만으로 RACE 이동은 완성되지 않는다.
- HUB와 RACE는 현재 같은 Place를 역할별 서버로 사용한다. 이번 설계를 위해
  무조건 별도 Place를 만들 필요는 없다.

### 아직 확인하지 않은 사항

- 외부 Mesh/Texture의 최종 운영 Experience 내 로드·접근 가능 여부와 사용 조건.
- 새 코스의 확정 크기·좌표·방향·고저차, 동시에 달릴 목표 인원과 기기별 성능 한계.
- 자동 카트 탑승 여부, TRACK VOTE 집계 범위·적용 시점, LEADERBOARD 표시 기준.
- 실제 모바일에서 새 공간을 장시간 달렸을 때의 성능.

**같은 HUB 서버 공유**와 **모든 HUB 서버 통합**은 구분한다. 현재 기반을 재사용하면
같은 서버의 사람들이 같은 도로를 달린다. 서로 다른 서버의 사람까지 한 장소로
모으려면 서버 배정·예약·이동 처리가 추가로 필요하며 본 1차 범위에 포함하지 않는다.

## 3. 공간 배치 제안

평면 배치의 첫 검토안은 다음과 같다. 최종 방위와 좌표는 기존 Lobby 출입구,
HubSpawn, 현행 RACE 지형과의 간섭을 측정한 뒤 정한다.

```text
        조경 / 배경 랜드마크 / 관람 지점
    ┌──────── 외곽 순환 주행 구간 ────────┐
    │   완만한 코너       Drift 연습 코너   │
    │                                    │
    │      보행 광장 + 외부 안내판          │
    │    TRACK VOTE     LEADERBOARD        │
    │          기존 HUB LOBBY             │
    │       GARAGE / 7대 전시 카트          │
    │                                    │
    │     카트 생성·탑승 구역 → 합류 차로     │
    └──────── 순환 / 피트 복귀 ────────────┘
```

- 카트는 진행 중인 주행 차로에 바로 생성하지 않고 별도의 탑승·합류 구역에서 준비한다.
- 사람이 안내판을 읽는 구역과 카트가 속도를 내는 구역을 분리한다.
- 기존 12-stud 보행 출입구와 TEST DRIVE 키오스크 접근 동선을 보존한다.
- Lobby 내부에서 주행 장면이 일부 보이도록 출입구 앞 시야를 열어 둔다.
- 주행 중 안내판 제목과 위치는 인지할 수 있어야 하지만, 작은 기록을 운전하면서
  모두 읽게 만들지는 않는다. 상세 내용은 안전한 광장/피트에서 확인한다.
- 역주행·마주 오는 카트 문제는 우선 진행 방향 안내와 기존 비충돌 정책으로
  다룬다. 새로운 강제 조향·자동 운전·충돌 페널티를 임의로 추가하지 않는다.

현재 Geometry의 구역 로컬 bounds는 X `-350..330`, Z `-90..252`이다. 이는 기존
구현의 측정 기준이며 새 파크의 승인 치수가 아니다. 1차 시안은 현재 크기에서
출발해 Lobby·주행·광장 동선이 성립하는지 확인한 뒤 확장한다.

### 기존 추출물부터 대조

`docs/KDM_PLACE2_ASSET_MANIFEST.md`, `src/assets/`, `KDMTemplateResources`,
`KDMPitGarageArt`, 기존 산·수목 Prefab을 먼저 확인한다. 같은 Mesh와 재질이
이미 있으면 재사용한다. 새 이름으로 중복 복제해 배포 크기를 늘리지 않는다.

**현재 F60 Lobby가 기준이다.** 원본 Garage는 추가 부품의 출처로 사용하며,
승인된 조명·전시 카트 방향·키오스크·UI가 적용된 현재 Lobby를 원본으로 덮어쓰지 않는다.

## 5. 실제 추출 도구와 산출물

추출은 Studio에서 원본 게임을 Play하는 방식 대신, 로컬 파일을 읽는 도구로 수행한다.
원본 네 파일은 수정하지 않는다.

1. 각 파일의 SHA-256과 파일 크기를 기록한다.
2. 원본 경로·클래스·하위 파트 수·바운딩 박스·MeshId·재질·Texture 의존성을 조사한다.
3. 중복 이름이 있는 `Kiosk`, `Vignette` 등은 전체 경로와 식별 정보/해시로 선택한다.
   첫 번째 같은 이름 모델을 무조건 선택하지 않는다.
4. 승인된 후보만 임시 추출 폴더로 내보낸다. Luau 도구라면 기존 Lune/Roblox
   역직렬화·직렬화 기능을 사용하고, 추출 결과를 다시 읽어 무결성을 확인한다.
5. `Script`, `LocalScript`, `ModuleScript`와 원본 게임의 Remote·태그 기반 동작,
   불필요한 Prompt/ClickDetector 등은 정적 외형에서 분리한다.
6. 보존할 Mesh·SurfaceAppearance·Texture·Decal·Attachment와 필요한 참조를 확인한다.
   모든 Joint를 일괄 제거하지 않고, 외부 대상을 가리키는 연결과 불필요한 정적
   Weld를 구분한다. 문이나 움직이는 전시 소품은 별도 후보로 분류한다.
7. 독립 모델로 로드하고 방향·Pivot·크기·재질을 검수한다. 배치 전후 모습을 캡처한다.
8. 실제 운영 소유권 조건에서 외부 에셋이 로드되는지 확인한 후보만 채택한다.

제안 산출물은 다음과 같다. 경로와 파일명은 구현 시 확정한다.

| 산출물 | 역할 |
| --- | --- |
| `tools/assets/extract_kdm_park_assets.luau` | 허용 목록 기반 반복 가능한 추출 도구 |
| `docs/assets/kdm_park_asset_manifest.md` | 출처·사용 조건·식별자·비용·채택 결과·전후 캡처 기록 |
| `src/assets/KDMHubParkPrefabs.rbxm` 등 | 선별·정적화된 소규모 모델 묶음 |
| `artifacts/hub-racing-park/` | 후보 비교, 임시 빌드, 캡처, 검사 로그; 커밋 제외 |

정적 장식은 기본적으로 Anchored=true, CanTouch=false로 만든다. 시각용 장식은
CanCollide/CanQuery=false를 우선 사용한다. 도로·안전 바닥·실제 벽은 주행과
Raycast에 필요한 충돌/쿼리를 별도로 유지한다. Mesh 외형과 단순한 충돌 형상을
분리해 복잡한 메시 이음새를 직접 주행하지 않도록 한다.

원본의 Lighting, SoundService, StarterPlayer, 실행 스크립트와 게임 설정 전체를
복사하지 않는다. 필요한 재질 의존성만 이름 충돌을 확인해 가져온다.

`HubLeaderboardService` 등의 역할로 나눌 수 있다. 이는 제안 이름이며 기존 기능과
중복되는 모듈을 무조건 추가하겠다는 뜻이 아니다.

새 형상은 한 데이터 정의에서 시각 도로, 충돌 경계, 생성 슬롯, 복귀 지점을
파생시키는 방향을 사용한다. 장식 도로와 서버가 허용하는 주행 영역이 서로 다른
두 개의 수동 좌표 목록으로 어긋나는 구조를 피한다.

## 7. 입장·카트 생성·무제한 순환

### 입장 동작 제안

사용자 의도에 가장 가까운 후보는 **도착 후 자신의 선택 카트를 자동 준비하고,
안전한 슬롯에서 정지 상태로 탑승시키는 방식**이다. 자동 탑승까지 적용할지는
화면/동선 검토에서 확정한다. 대안은 기존 TEST DRIVE 한 번으로 즉시 탑승하는 것이다.

자동 탑승을 채택한다면 다음 순서로 구현한다.

1. HUB 역할·살아 있는 캐릭터·선택 카트·진입 가능 상태를 서버에서 확인한다.
2. 이미 진입 대기/탑승 중이면 동일 요청으로 카트를 중복 생성하지 않는다.
3. 안전 슬롯을 예약한 뒤 캐릭터/시트가 준비되면 탑승한다. 입력은 초기화하고
   가속하지 않은 상태로 시작해 로딩 중 차가 혼자 움직이지 않게 한다.
4. 슬롯 부족이나 로딩 실패 시 기존 보행 Spawn과 TEST DRIVE 접근을 유지한다.
5. 하차하면 광장으로 복귀할 수 있어야 한다. 의도적으로 내린 사람을 곧바로
   다시 자동 탑승시키지 않도록 입장 사유와 generation을 구분한다.

자동 준비는 매 프레임 실행하거나 캐릭터 이벤트마다 무조건 반복하지 않는다.
자유 주행 중 레이스 종료/랩 수에 따른 강제 탈출은 추가하지 않는다. 계속 도는 동안
새 카트를 생성하지 않으며, 사망·이탈·레이스 이동·하차 시 기존 정리를 재사용한다.

시작 슬롯은 무제한 늘리지 않는다. 현재 구현도 슬롯이 주행 경계 안에 들어가는지
확인하므로, 동시 주행 목표와 피트 크기에 맞춰 유한 슬롯/대기 정책을 정한다.
운영 서버의 최대 접속 인원을 곧바로 동시 주행 보장 인원으로 간주하지 않는다.

## 8. 고저차·터널·안전 구간

1차 검증용 코스는 평면 또는 기존 물리로 검증 가능한 완만한 형상부터 만든다.
이미지의 고가도로·교차 터널은 후속 구현 단계다. 삭제하거나 불가능하다고 보는 것이
아니라, 현재 X/Z 경계만으로 위·아래 도로를 구별할 수 없기 때문이다.

고저차를 도입할 때는 도로 구간과 높이, 진행 방향, 연결 구간을 구별하고 도로
하부/상부를 잘못 복귀 지점으로 선택하지 않도록 한다. 경사 접속부·지붕·터널
카메라·수직 낙하·통신 지연 상태에서 실제 접지와 복구를 검증한다. 위치를 강제로
도로 높이에 붙이거나 새로운 주행 물리로 교체하는 방식을 임의 적용하지 않는다.

새 도로에는 저장소의 KDM Track Visual & Safety Standard v1을 적용한다.
양쪽 연속 Kerb, ROAD → KERB → SHOULDER → BARRIER 순서, 일반 12 / 주요 Drift
16 / Drift 출구 18 studs 이상의 안전 여유를 지킨다. 진행 화살표는 실제 접선과
일치시킨다. 도로 폭과 코너 반경은 기존 카트의 회전·Drift로 통과 가능한지 먼저
확인하고 확정한다. 비접촉 정책이 있더라도 벽/장식이 주행 선을 침범하지 않게 한다.

## 9. 외부 TRACK VOTE와 LEADERBOARD

### 공통 표현

실제 기둥/프레임에 붙은 SurfaceGui를 우선 사용한다. 광장에서 보이는 제목과
근접 시 읽는 상세 내용을 구분하며, 모바일 화면 중앙에 큰 상시 Billboard를 띄우지
않는다. F60의 좌측 세 메뉴·우측 두 행동·상단 프로필/지갑은 유지한다.

보행 경로에서 제목이 보이고 접근하면 기존 모달 계층으로 상세 창을 열 수 있게 한다.
차량 탑승 중에도 보기/상호작용을 허용할지는 입력 충돌과 함께 확정한다. UI가
핸들·아이템 입력을 동시에 실행시키지 않아야 하며 터치 대상은 44px 이상 확보한다.

### TRACK VOTE: 표시와 정책을 나눠 구현

| 항목 | 제안 / 확정 필요 내용 |
| --- | --- |
| 초기 범위 | 같은 HUB 서버의 투표로 제한하는 안 |
| 권한 | 서버가 TrackCatalog의 허용 TrackId, 실제 접속자, 요청 빈도를 검증 |
| 중복 처리 | 사람당 현재 선택 1개; 변경 가능 여부와 마감 규칙은 승인 후 확정 |
| 생명주기 | 이탈·재접속·새 투표 라운드 처리와 동률/0표 정책 정의 필요 |
| 표시 | 변경 시 또는 제한된 주기에 결과 갱신; 매 프레임 복제 금지 |
| 저장 | 첫 구현에는 신규 영구 저장 없이 서버 메모리 사용 |
| 매칭 적용 | 어떤 RACE NOW 요청/그룹/다음 레이스에 적용할지 별도 승인 필요 |

단순한 다수결로 모든 사람의 선택 TrackId나 이미 생성된 방/예약을 덮어쓰지 않는다.
투표 승리 트랙 표시와 실제 매칭 정책을 분리한다. 첫 시안의 정적 화면은 시안임을
표시하고 실제 투표·접속자 수처럼 보이는 가짜 값을 운영에 노출하지 않는다.

### LEADERBOARD: 공식 기록 범위를 먼저 고정

서버에 공식 기록과 OrderedDataStore 인덱스 쓰기 경로가 있지만, 외부 공용 순위판의
완성된 조회 API가 있다고 가정하지 않는다. Track/Geometry/Ruleset/참가 구분/랩 수가
다른 기록을 섞지 않도록 현재 기록 키와 인덱스 scope를 조사한다.

표시 대상은 예를 들어 '선택 트랙의 검증된 Best Race 상위 기록'으로 정할 수 있다.
Best Lap, 사람 전용, 봇 포함, 전체/기간별 중 무엇을 쓸지는 승인 사항이다.

- 조회는 서버에서 수행하고 공유 캐시·요청 합치기·쿨다운을 둔다.
- 플레이어마다, 매 프레임 DataStore를 읽지 않는다.
- 조회 실패 시 준비 중/갱신 지연을 표시하고 주행을 막지 않는다.
- 이름·아바타 조회도 캐시하며 보드 근처 이동으로 반복 요청이 폭증하지 않게 한다.
- 기존 프로필의 K$·소유권·개인 기록과 저장 스키마는 변경하지 않는다.
- MY PROFILE 내부 MY RECORDS의 기존 접근 제한은 유지한다. 공용 순위판에
  공개할 이름·기록 필드를 별도로 확정하며 개인 프로필/구매 정보까지 노출하지 않는다.
- 기존 `KDMGetPersonalRecords`는 개인별 조회와 관리/복구 분기가 있는 경로이므로
  공용 순위판의 반복 조회 API로 그대로 사용하지 않는다. 보드용 조회는 기존
  인덱스와 정책을 확인한 뒤 별도의 읽기 전용 경로로 구성한다.

## 10. 자유 주행에서 RACE로 이동

첫 단계는 **하차/시승 종료 → 기존 LobbyPostDriveView → RACE NOW → QuickStart**를
유지한다. 주행 중 직접 RACE NOW를 원하면 다음 별도 단계를 적용한다.

```text
서버가 이동 요청 확인
 → 시승 입력 차단·상태 전환
 → 기존 stopLobbyDrive/Service.stop 경로로 안전한 하차·카트 정리
 → 종료 확인 및 기존 QuickStart/예약·admission 검증
 → 레이스 서버 이동
```

기존 서버 API와 실제 호출 순서를 조사해 기존 동작과 동일한 진입점을 사용한다.
클라이언트의 버튼 처리에서 `LobbyDriveActive` 가드만 제거하지 않는다. 연속 클릭,
하차 중 사망, 매칭 실패, 텔레포트 실패에 대한 복귀 상태를 정의한다. 실패했다고
옛 카트와 새 카트를 동시에 살리거나 예약 검증을 건너뛰지 않는다.

## 11. KDM RACE의 세계관 확장

공식 RACE도 도로와 그 주변이 하나의 장소처럼 느껴지도록 발전시킬 수 있다.
예시는 피트·관람석이 있는 레이싱 파크, 외곽 도시 경기장, 성벽/다리를 지나는
코스다. 이 테마를 어느 기존 Track에 배정할지는 아직 승인되지 않았다.

먼저 기존 주행 도로와 기록을 바꾸지 않는 배경/랜드마크 시안을 만든다. 도로
기하가 달라지는 개편은 별도 작업으로 분리하고 GeometryId/Ruleset과 기존 기록의
비교 가능성을 검토한다. 도로 변경 후 과거 기록을 같은 조건의 기록처럼 유지하지 않는다.

HUB 파크와 각 RACE는 색상·간판·Kerb·광고 배너 등 KDM 공통 언어를 공유하되,
HUB 장식을 RACE 서버에 모두 생성하지 않는다. 현재 같은 Place의 역할 분기를
유지하면서 필요한 환경만 구성할 수 있다. 이 문서만으로 기존 Figure 8 또는
Track02/03 지형을 변경하지 않는다.

## 12. 모바일 성능·저장·주행 보존 조건

### 에셋과 로딩

- 처음에는 원본 맵 전체가 아닌 적은 종류의 Prefab을 반복 배치한다.
- 가까운 주행면/표지판은 선명하게, 먼 건물/수목은 낮은 세부 수준으로 구성한다.
- 새 HUB 전용 원본은 필요하다면 ServerStorage에 두고 HUB 역할에서만 배치한다.
  ReplicatedStorage에 큰 원본 묶음을 넣고 숨기기만 하면 클라이언트 로딩을 줄인
  것으로 볼 수 없다. 기존 자산 전체의 저장 위치 변경은 별도 범위다.
- 광원은 필요한 곳에 한정하고 실시간 그림자·반투명 겹침·파티클 밀도를 제한한다.
- Streaming 적용은 코스 전체를 보며 주행할 때의 시야, 미로드 도로, 카메라와
  차량 복제를 함께 검증한 뒤 결정한다. 무조건 켜면 해결된다고 가정하지 않는다.

Roblox 문서는 스트리밍으로 로딩/메모리 부담을 줄일 수 있다고 설명하지만,
Studio 에뮬레이터는 실제 모바일 메모리 검증을 대신하지 못한다고 명시한다.
참고: [성능 설계](https://create.roblox.com/docs/performance-optimization/design),
[인스턴스 스트리밍](https://create.roblox.com/docs/workspace/streaming).

### 변경하지 않을 계약

- 승인된 Race 속도·Nitro·Mini Boost·조향·Drift·아이템·보상 금액과 P0 멱등성.
- 여섯 아이템 기본 출발, 비최종 랩의 비-Nitro 빈 항목만 1 보충, 5 BOOST Nitro 정책.
- 수동 서버 소유권을 탑승 이후에도 유지하는 기존 PV931 수명주기 가드.
- 실제 플레이어/봇 구별, 카트 정리, 공식 기록 검증과 크로스서버 예약/admission.
- 제거한 `DEMO · NOT A PLAYER`와 `LIVE TEST DRIVE` 표시를 이 작업을 이유로 복원하지 않음.

PV932의 5–15회 Rematch 후 주기적 멈춤은 현재 미해결이다. 새 HUB 시안 개발은
분리해서 할 수 있지만, 시각 개선으로 해당 문제가 해결됐다고 선언하지 않는다.
배포 판단에는 기존 RACE 장기 반복과 새 HUB 장기 순환 검증을 모두 포함한다.
참조: `docs/testing/rematch_hitch_followup.md`.

## 13. 단계별 실행과 검토 산출물

| 단계 | 실제 작업 | 검토 산출물 / 다음 단계 조건 |
| --- | --- | --- |
| P0 기준 고정 | HEAD/Dirty 확인, 기존 F60 화면·도로·입장 동작 측정 | 기준 캡처, 코드/에셋 목록; 사용자 변경 보존 |
| P1 에셋 선별 | 허용 목록·의존성·권한 확인, 소수 후보만 정적 추출 | 에셋 목록·개별 미리보기·재사용/보류 판정 |
| P2 단순 지형 시안 | 기존 Lobby를 중심으로 도로·피트·광장·보드 위치 구성 | 상면도, 출입구/Spawn/운전 시점 PC·모바일 캡처 |
| P3 공유 주행 연결 | 기존 시승 서비스에 새 경계/슬롯 연결, 입장 방식 검증 | 1/2/4인 생성·주행·하차·정리와 장기 주행 결과 |
| P4 외부 보드 | 읽기 가능한 배치; 승인된 투표/순위 데이터 기능만 구현 | 서버 권한·오류·조회 횟수·모바일 상호작용 검증 |
| P5 외형 마감 | 채택 Prefab·KDM 간판·조경·조명·배경 적용 | 동일 시점 전후 비교, 성능 비용과 회귀 결과 |
| P6 릴리스 검토 | 실제 기기, 장기 반복, 전체 회귀·빌드·Diff 검토 | 승인된 Commit 목록과 별도 Publish 판단 |

각 단계는 시각 검토 가능한 작은 결과로 제출한다. 정책 미정 항목이 있으면 그 항목의
의존 작업만 보류하고 에셋 선별·단순 지형 시안 등 독립 작업을 진행할 수 있다.
코드 기본값을 몰래 바꿔 기존 HUB와 새 HUB를 동시에 중복 생성하지 않는다.
전환 플래그가 필요하면 기본 경로·실패 시 기존 환경 복귀·해제 방법을 함께 검증한다.

테스트 코드의 후보 연결점은 기존 `h1_shared_drive_service_validation`,
`lobby_test_drive_validation`, `lobby_practice_layout_validation`,
`lobby_post_drive_return_validation`, `f60_c2_lobby_layout_validation`,
`race_network_ownership_validation`, `datastore_idempotency_validation` 등이다.
현재 통과 여부는 구현 시 다시 실행해 판정하며 이름 목록을 PASS 증거로 사용하지 않는다.

관련 테스트와 전체 회귀를 다시 실행하고 기존 실패 집합과 비교한다. 기존 실패를
임의로 PASS 처리하거나 보안 Assertion을 약화하지 않는다. Production Luau 컴파일,
일반 Rojo XML/바이너리 빌드, `git diff --check`를 수행한다. 운영 DataStore 쓰기
실험은 하지 않으며 Studio/격리 환경과 실제 게시 환경의 결과를 구분한다.

## 15. 구현 착수 전 확정할 항목

1. HUB 첫 도착: 자동 카트 준비·탑승인가, TEST DRIVE 한 번으로 탑승인가?
2. 1차 코스: 평면 순환부터 승인하고 고저차를 다음 단계로 할 것인가?
3. 동시 주행 목표 인원과 그 이상 인원에 대한 시작 슬롯/대기 방식은 무엇인가?
4. TRACK VOTE의 대상 사람·기간·동률·승리 트랙 적용 대상은 무엇인가?
5. LEADERBOARD의 트랙·기록 종류·참가 구분·기간은 무엇인가?
6. 시승 중 직접 RACE 이동을 포함할 것인가, 기존 하차 후 이동을 유지할 것인가?

이 중 미정 사항은 제안서에 남겨 두며 이 문서로 자동 승인하지 않는다. 최종 도면과
첫 단계 범위를 검토한 뒤 실제 에셋 추출과 코드 변경에 착수한다.

## 16. 문서 작성 시점의 작업 결과

이번에는 설계 문서만 추가했다. 네 원본 파일과 기존 게임 소스/에셋은 수정하지
않았고, Studio 실행·운영 데이터 변경·Roblox Publish도 수행하지 않았다.
따라서 새 파크의 Studio runtime 및 실제 모바일 검증은 **아직 미실행**이다.
문서만 저장소 규칙에 따라 선택적으로 Commit/Push하며 구현 승인과 구분한다.
